# 同 provider 增量模型补齐：优化设计提案

状态：设计提案，尚未实施。本文替代“新增 refresh-* 全量 provider”作为目标方向，不代表当前已安装镜像版已经改变行为。

## 1. 目标只保留一件事

**让新模型出现在原 provider 的原列表里，原模型继续由原实现负责。**

```text
原 provider 原生目录 A ────────────────┐
                                       ├─ 按 ID 合并 ─> 原配置解析 ─> 同一个原 provider
插件维护的新增模型 Δ ──────────────────┘
```

使用默认目录时，最终列表是 `A + Δ`；存在显式 models 名单时，仍按该名单筛选、解析合并后的目录，插件不擅自扩展白名单。

- 不新增 provider ID、不要求用户换路由、不修改默认模型或历史会话。
- 不更新或删除原列表已有 ID，不覆盖其能力、名称或用户自定义设置。
- 插件只管理自己的新增记录，不再维护一套旧模型的运行时镜像。
- 不做通用 provider 编辑器，不下载执行新版驱动，不修改安装包。

首次候选差集：`Δ候选 = 上游模型 ID − 原生目录 ID − 用户已有显式模型 ID`。计算范围严格限定到同一个已配置 provider，不跨服务商按 ID 猜对应关系。

这里减去的是完整原生目录，而不仅是当前界面可见列表：用户通过显式名单过滤掉的旧模型，不能被误当成“新模型”补回来。

## 2. 已核实的当前约束

核对对象：安装版 `@deepseek-ai/dsh-llm-pi-ai` Core 包 0.2.1-rc.2，并对照官方文档；文档主分支不作为目标版本保证。

| 当前公开能力 | 含义 |
|---|---|
| provider 的 `models` | 替换原目录，不是追加 |
| `modelOverrides` | 只能改已有原生 ID，不能增加新 ID，且不能与 `models` 并用 |
| 模型配置字段 | 有容量、模态、推理映射和部分 compat；没有逐模型 `api` / `baseUrl`，也不能表达全部原始 pi-ai 字段 |
| 新 ID 的协议解析 | 依赖原 route 的 `api` 或原生目录唯一协议；混协议 route 不能无条件追加未知 ID |
| `registerAdapter` | 原 provider 已有 adapter 时拒绝重复注册；不能把第二个 adapter 同名挂上去补模型 |

因此，不能把“直接追加几个 ID”或“同名再注册 adapter”当成当前 Core 已支持的通用方案。

## 3. 方案比较与推荐

| 路径 | 原列表内补充 | 对现有配置的影响 | 主要代价 |
|---|---|---|---|
| 当前镜像版 | 否，需要另选 refresh-* | 不改原配置 | 重复全量 provider，偏离目标 |
| A：配置层合并物化 | 可以，但有协议/端点/字段限制 | 将原有效名单与新增项合并写入原 route 的 models | 名单物化、modelOverrides 转换、外部编辑冲突、显式撤回事务 |
| B：正式目录增量扩展点 | 可以，原 adapter 消费新增完整记录 | 不写原 provider 配置 | 需要 DSH 先提供并发布一个正式扩展点 |

**推荐 B 作为最终设计；A 仅作为“不升级 Core”时的受限兼容方案，不自动回退。**

这不是建议给现有方法打运行时补丁。B 需要在 DSH 的正常源码开发/发布流程中提供公开能力，插件随后消费该接口；不能就地修改 ASAR、替换核心文件、篡改 adapter 私有对象或冒充已存在的 API。

当前已核实的公开接口不足以直接实现 B。设计评审后若坚持只用当前 Core，必须明确选择 A 的限制，不能继续用额外 provider 伪装成原位补充。

## 4. 推荐结构：插件发布增量，原 adapter 负责合并

### 4.1 职责分离

**插件保留：**
- 获取并校验最新 pi-ai JSON 数据；不执行下载代码。
- 计算新增差集、校验完整模型描述，缓存已接受的增量。
- 后台刷新、补充数量与待确认原因。已有官方清单核对设施可复用，但不是首版增量接口的新增工作项或必需验收前提。

**原 llm-pi-ai 负责：**
- 原目录、用户 models/modelOverrides 和现有连接设置的解析。
- 在自身模型集合中合并被接受的增量，保持原 provider 身份。
- 通过原有 listModels / resolveModel / prepareCall 路径提供新模型。
- 原有认证、OAuth、请求头、附件、重试、流式及历史回放路径。

因此不再需要插件自己的 PiAiAdapter、镜像 provider、推理凭据桥接或 provider 身份来回改写。原始下载缓存可能包含整包数据，但插件发布和管理的运行时集合只包含增量。

### 4.2 拟议扩展点的最小合同

以下是待实现能力描述，不是当前可调用的函数名：

```text
注册补充(target = 配置 namespace + 原 route, owner, 完整模型记录) -> handle
handle.replace(下一代增量快照)
handle.dispose()  // 只撤销此 handle 拥有的补充
```

扩展点放在原 llm-pi-ai 的**原生默认目录读取之后、用户配置解析之前**：先形成原生优先的 `A ∪ Δ`，再走既有 models / modelOverrides、连接与能力解析。不能只向选择器塞一份展示数据，必须同时影响模型解析和真正的请求准备。

合同必须保证：
1. **目标唯一。** 绑定明确的原实例/route；目标消失时等待或撤销，不另建 provider。
2. **原条目优先。** 同 ID 已由原有效列表提供时，补充不覆盖。不同补充者之间同 ID 冲突明确拒绝，不采用最后写入者获胜。
3. **完整校验。** 新记录携带协议、容量、模态、compat、thinkingLevelMap、inputLimits、cost 等原生信息；原驱动不能服务或无法确定可信端点时不发布。
4. **单代快照。** 列举、模型解析、请求准备读取同一代集合；已准备请求保留旧快照，失败不提交半成品。
5. **生命周期归属。** 停用只撤补充；原 provider 的注册、配置和凭据不动。结果回到未启用补充时的原有效列表。
6. **通知变化。** 补充发布、撤销和原生接管产生可观察的目录失效通知，不要求用户改默认模型。
7. **能力协商。** 扩展点须有可检查的接口版本；缺少支持时只保留候选/诊断，不自动改配置、不创建镜像路由，也不 monkey-patch 原 adapter。

### 4.3 用户配置与原生接管

唯一定义：`A` 为安装版原生目录，`Δ` 为已接受补充；`B = 原配置解析(A)` 是未启用补充时的实际有效列表，`E = 原配置解析(A ∪ Δ)` 是启用后的有效列表。

优先级明确为：**显式 models 名单决定可见性；用户显式字段 > 原生记录 > 补充默认字段**。不同补充者之间同 ID 冲突先拒绝，不参与覆盖排序。名单更新控制后续新代查询/请求，已准备的请求仍持有旧快照。modelOverrides 在既有互斥规则允许时经过同一配置解析路径，不被补充层绕过。

- 保留原列表的顺序、显式成员、modelOverrides 和自定义参数；默认目录模式下新增项追加，不重排旧项。
- 显式 models 是用户筛选意图，默认不绕过：补充记录可成为目录中的候选，但只有已列入该名单的 ID 才会显示/可用。没有改变原名单时，不宣称该 route 已自动补齐可见列表。
- 不把原生目录中被用户过滤的旧 ID 当成新增；不反向修改原名单。若要自动扩展显式名单，应先另行明确这一产品规则，不在本提案中悄悄增加写配置行为。
- Core 升级后，某补充 ID 已存在于原生目录 A：原生记录接管，补充不再提供该 ID。之后仍由原 models / modelOverrides 决定可见性和定制；不能为了维持补充数量绕过用户白名单。
- 接管前后都是同一个 ID，经原配置层解析；默认目录模式下应保持可见、无重复，已有显式名单里的该 ID 也应继续解析为原生记录。

### 4.4 失败与删除策略收敛

本功能是“补新”，不是“维护全量目录”：
- 首次差集只用于发现；后续发现还需减去已接受 ID，避免重复计为新增。已接受增量独立更新/保留，不因再次做差集被误删；原生同 ID 接管时才按接管规则退出。
- 刷新失败保留已接受的增量，不影响原目录，也不凭一次上游漏项自动删除补充项。
- 缺少协议支持或完整描述的候选只显示待确认原因，不注册假可用项。
- 不更新已有原生模型元数据，不做旧模型清理；原实现升级后的变化由原实现负责。
- 官方核对使用原 route 的既有凭据引用，仅作清单证据；不改变推理鉴权，也不持久化密钥。

## 5. 如果选 A：必须明确承认的边界

A 可复用 [provider-config.mjs](../lib/provider-config.mjs) 的配置编辑、并发核对与归属思路，但不能把已有通用手动 provider 管理器重新搬回来。

- 用 configEditor 修改原 route。写入 models 时，若原有 modelOverrides，必须把其值内联到对应原条目并删除原 modelOverrides 键（两者互斥）；这是配置形态变化，不是无副作用的追加。除此之外不创建 provider，不改原 route 的 api、baseURL、凭据或请求头。
- 没有显式名单时，先物化原有效名单，再加增量；已有名单时保留原条目，不能用上游全量覆盖它。
- 原生条目可只写 ID 与用户覆盖字段：当前 Core 用同 ID 的原生记录作为未填写字段的默认值（resolveEntry 中先取 defaults.get(entry.id)，容量等先 entry 再 base）。因此“成员名单被物化”与“所有元数据被冻结”不是一回事。未知 ID 不能靠 bare ID 假定完整；它仍须提供可表达的必要字段。插件还需要持续合并原生新增成员，避免成员名单永久冻结。
- 只有原 route 的既有协议与端点能安全表达新增项时才能应用。混协议、缺端点、动态表达式或不能表达的必要 vendor 字段进入待确认；不强改整个 route 的协议来迁就一个新模型。
- 每次写入验证“当前值仍是预期值”，外部编辑冲突时停止覆盖。撤回只移除仍可证明属于插件的项；保留用户后续改动。
- 配置已经持久化，停用插件不会像 B 一样自然撤销变更。需要显式、经过冲突核对的撤回动作；因此 A 的恢复复杂度不会消失。

A 能减少安装目录写入，但不能同时获得 B 的无配置写入、多协议完整记录和自然生命周期撤销。不能对所有原 provider 宣称通用可用。

## 6. UI 与代码收敛

UI 继续使用原 provider 卡片/现有设置页，只显示“补充新模型”、已补充数量、候选和待确认原因。不新增 provider 分组、不提示换到 refresh-*，不增加通用 provider 创建功能。

已有数据获取、完整记录校验、后台队列和诊断逻辑可复用；镜像 adapter/provider 注册及全量镜像状态退出目标架构。旧恢复记录仍保留，不把设计切换变成自动恢复旧 catalog 的动作。

本轮只形成方案。以下属于后续迁移阶段，不是首版目录扩展接口的验收前提：先验证原 route 的新增模型能够列举、解析并准备请求，再处理旧镜像入口；已选择 refresh-* 的测试会话需明确切回原 route，不偷偷改写会话或默认模型。

## 7. 最小验收

- 原 provider ID、连接设置和原有效模型集合不变；只增加验证通过的新 ID，无另一份全量列表。
- 同 ID 不重复、不覆盖；被用户筛掉的旧模型不复活。
- 新 ID 真正经过原 adapter 请求准备，不是仅出现在前端。
- 混协议按模型正确 dispatch，不能把旧模型整体改为一个协议。
- 刷新失败不损坏原模型；并发编辑/发布失败不提交部分状态。
- B 停用仅撤自己的增量；原列表已有条目和原生接管项不受影响。
